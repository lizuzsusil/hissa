# Hissa — Firebase Auth + Firestore Implementation

This document walks through every step taken to replace the in-memory demo
backend with real Firebase Authentication and Cloud Firestore persistence,
plus the steps that still need to be done by hand (console setup, rules
deploy).

## 3. Repository interface made async

`lib/data/repository.dart` — the persistence boundary. Mutations are now
`Future<void>` so the Firestore implementation can await writes; reads stay
synchronous over locally-cached lists.

Added two query methods:

```dart
Future<Household?> findHouseholdByInviteCode(String code);
Future<String?> findHouseholdIdForUser(String userId);
```

### 3a. `InMemoryRepository` (`lib/data/in_memory_repository.dart`)

Implements the async interface. The method bodies contain no `await`, so the
mutation still happens synchronously — seed builders and unit tests that do
not `await` continue to work unchanged. `findHouseholdByInviteCode` and
`findHouseholdIdForUser` search the local lists.

## 4. `FirestoreRepository` (`lib/data/firestore_repository.dart`, new)

A `FirestoreRepository implements ExpenseRepository`.

### Design

- **Reads**: synchronous getters over in-memory caches that are kept fresh by
  realtime Firestore listeners, so the UI can rebuild eagerly.
- **Writes**: update the local cache immediately (optimistic), then `await`
  the Firestore write.
- **Lifecycle**: `start(uid:, householdId:, onChanged:)` tears down old
  listeners, loads an initial snapshot, and subscribes to realtime updates.
  `stop()` cancels all listeners and clears caches.

### Document-id conventions

```
users/{userId}                                   global (uid or pseudo-user id)
households/{householdId}                         global
householdMembers/{householdId}_{userId}
categories/{householdId}_{id}
cycles/{householdId}_{id}
expenses/{householdId}_{id}
expenseShares/{householdId}_{id}
settlements/{householdId}_{id}
```

Prefixing with `householdId` prevents id collisions across households
(important for default categories like `cat_groceries` that are created per
household). Household-scoped documents also store a `householdId` field so
security rules can enforce membership and queries stay scoped.

### Subscriptions (per household)

- `households/{hid}` — document listener
- `householdMembers` where `householdId == hid`
- `categories`, `cycles`, `expenses`, `expenseShares`, `settlements` where
  `householdId == hid`
- `users/{uid}` — own profile
- `users/{member.userId}` for each member (hydrates pseudo-user profiles)

Each listener replaces the matching cache list and calls `onChanged`
(`notifyListeners` in the app).

### Write semantics

- `saveExpense` writes the expense document and replaces all
  `expenseShares` for that expense inside a Firestore **batch** (deletes
  existing shares, writes new ones).
- `deleteExpense` deletes the expense and its shares.
- `saveMember(member, [householdId])` — householdId is optional because the
  `HouseholdMember` model has no household reference; the Firestore
  implementation throws if it can't resolve one.
- `writeAll(...)` — bulk seeder helper used by the demo login. Members are
  written **before** households so rules (which gate household writes on
  membership) accept the very first seed.
- `findHouseholdByInviteCode` / `findHouseholdIdForUser` are Firestore
  queries.

### Error handling

Initial loads and listeners swallow errors (e.g. permission-denied) and
degrade to an empty cache rather than failing the whole attach flow.

## 5. `AppState` (`lib/state/app_state.dart`) — real auth + Firestore

`ExpenseRepository _repo` now starts as an `InMemoryRepository()` and is
swapped for a `FirestoreRepository` once signed in.

### Session restore

`load()` reads the intro flag and the session blob (household/cycle
selections) from `SharedPreferences`, then checks
`FirebaseAuth.instance.currentUser`. Firebase persists the signed-in user
across launches, so a cold start restores the session without a password.

### `_attachRepository()`

The heart of the switch-over:

```dart
Future<void> _attachRepository() async {
  final uid = _currentUserId;
  if (uid == null) return;
  if (_repo is FirestoreRepository) ( _repo as FirestoreRepository).stop();

  final repo = FirestoreRepository(FirebaseFirestore.instance);
  final householdId = await repo.findHouseholdIdForUser(uid); // may be null
  _householdId = householdId;
  _repo = repo;
  await repo.start(uid: uid, householdId: householdId, onChanged: notifyListeners);
}
```

The household is re-derived from Firestore membership every time, so it stays
correct after joining a new household.

### Auth methods

| Method | Behaviour |
| --- | --- |
| `signIn(email, password)` | `FirebaseAuth.signInWithEmailAndPassword`, returns `false` on a `FirebaseAuthException`. |
| `signUp(name, email, password)` | `createUserWithEmailAndPassword`, then writes `users/{uid}` profile. |
| `signInDemo()` | `signInAnonymously`, seeds Firestore via `seedDemoFirestore`, signs in as Ram in `h_demo`. |
| `signOut()` | stops the repo, resets selections, calls `FirebaseAuth.signOut()`. |
| `updateProfile(name)` | updates `users/{uid}` and the matching membership doc. |

### Household mutations

- `createHousehold` writes the **owner membership before the household** so
  rules accept the create, then pseudo-user members, default categories and
  an active cycle, then re-attaches to the new household.
- `joinHousehold` looks up the invite code via
  `findHouseholdByInviteCode`, adds its own membership, and re-attaches.
- `addMember` / `removeMember` / `renameHousehold` /
  `renameHouseholdCurrency` await the Firestore writes.
- `_seedCategories` now reuses `kDefaultCategories` from
  `lib/core/constants.dart` (consistent palette).

### Misc

- `dispose()` stops the Firestore repository.
- `selectCycle` is now `Future<void>`.

## 6. Demo seed (`lib/data/seed.dart`)

Added `seedDemoFirestore(FirebaseFirestore db, String uid)`:

1. Builds the in-memory demo dataset with `buildSeedRepository()`.
2. Remaps the seeded owner `u_ram` → the anonymous user's `uid` across
   users, members, expense `paidByUserId`, share `userId`, and settlements.
3. Persists everything with `FirestoreRepository.writeAll(...)`.

This makes the anonymous demo user a real member of `h_demo`, which
satisfies the security rules. The demo button can be tapped repeatedly
(`set` is idempotent).

## 8. Firestore security rules & indexes

### `firestore.rules`

Membership is keyed on the existence of a membership document:

```
householdMembers/{householdId}_{request.auth.uid}
```

Rules summary:

| Collection | Read | Write |
| --- | --- | --- |
| `users` | any signed-in user | create: any signed-in; update/delete: own profile only |
| `households` | any signed-in user (so invite-code joins work) | members of that household |
| `householdMembers` | own membership or members of the household | create: own membership or member; update/delete: member |
| `categories`, `cycles`, `expenses`, `expenseShares`, `settlements` | members of `resource.data.householdId` | members of `request.resource.data.householdId` |

### `firestore.indexes.json`

One composite index is required:

```json
{
  "collectionGroup": "expenseShares",
  "queryScope": "COLLECTION",
  "fields": [
    { "fieldPath": "householdId", "order": "ASCENDING" },
    { "fieldPath": "expenseId", "order": "ASCENDING" }
  ]
}
```

Used by `saveExpense` / `deleteExpense` to find shares for an expense.

## 10. Manual steps (outside the code)

These cannot be done from the repository and must be completed once:

1. **Create/select a Firebase project** (Firebase console), then:
   ```bash
   flutterfire configure
   ```
   This regenerates `lib/firebase_options.dart` with the correct project id.

2. **Enable Authentication** → Sign-in method:
   - Email/Password
   - Anonymous

3. **Deploy Firestore rules and indexes** (from the project root):
   ```bash
   firebase deploy --only firestore:rules,firestore:indexes
   ```

4. (Optional) If you want real pushes/analytics later, enable Cloud
   Messaging, Analytics, App Check, Storage, and Functions in the console and
   add the corresponding platform config.

5. Run the app on a device/emulator (web is fine too):
   ```bash
   flutter run
   ```
   Sign up with email/password, create a household, and try the demo login.
   Data survives restarts and is shared across devices signed into the same
   account.

## Known trade-offs (accepted for this milestone)

- `households` is readable by any signed-in user (not just members) so
  invite-code joins can query it. Expenses, shares, members, etc. remain
  membership-gated.
- Single-household assumption: the app loads one household per session; the
  first membership found wins. Multi-household membership is not surfaced.
- Pseudo-users (members added by name, e.g. `u_<genId>`) exist in `users`
  with a `@hissa.app` email and cannot log in.
- Offline writes degrade gracefully on permission/network errors (empty
  cache, silent) — no offline queue yet.
